# Project: Job Poster Analyzer

Next.js (App Router) + TypeScript + Tailwind app that turns a photo of a job-posting poster (English, Sinhala, or Tamil) into structured job-listing data, using a vision AI model (the provider is swappable — see "AI provider layer" below; currently Gemini), then lets a human review/correct the result in a form before (eventually) posting it.

## Request flow

0. `app/page.tsx` — public home/landing page (ikman.lk-themed). The user logs in with their ikman.lk account through the header's Login popup, then lands on `/upload`. `/upload` and `/job-form` require login — see "Auth: app login" below.
1. `app/upload/page.tsx` — user uploads a poster image (`app/components/ImageUploader.tsx`), then POSTs it to `/api/extract`.
2. `app/api/extract/route.ts` — checks the app login (see "Auth: app login"), validates the (client-resized, see "AI provider layer" below) image, sends it with the extraction prompt to whichever AI provider `AI_PROVIDER` selects (`lib/ai`), and turns the JSON reply into a `JobDetails` object (`lib/jobExtraction.ts`), normalizes `jobCategory`/`jobRole` against the taxonomy (see below), and returns it.
3. The client stores the result in `sessionStorage` (`jobData`, `extractionSuccess`, `extractionError`, `extractionErrorCode`) and navigates to `/job-form` — on failure too, so the user can still fill the form in manually (see "Extraction errors & logging" below).
4. `app/job-form/page.tsx` — reads `sessionStorage`, renders an editable form pre-filled with the extracted data. If the poster advertises the same role across multiple locations, one tab per location is shown (see below); otherwise the form renders directly with no tabs. Fields the AI couldn't determine are highlighted green and left for manual entry.
5. "Post Job" POSTs `{ job: jobForms[activeTabIndex] }` to `app/api/post-job/route.ts`. What happens next depends on `POST_JOB_METHOD` (`lib/features.ts`, set at build time in `next.config.ts`):
   - **`extension`** (the default on Vercel): the route answers with a hand-off (`PostAdHandoff`: ikman.lk's post-ad form URL for this category + town, and every field value in the form's formats), and the job form passes it to the **ikman Job Poster browser extension** (`extension/`). The extension opens ikman.lk's form in a new tab of the user's own browser, fills it in, and the user checks it and clicks "Post ad". See "Posting: browser extension" below.
   - **`browser`** (the default everywhere else): the route calls `automation/postJob.ts`'s `postJob` — a server-side Playwright browser that starts **already logged in to ikman.lk as the user logged into this app** (their app session token is loaded into it as ikman.lk's login cookies — no second login; see "Domain: Ikman.lk login credentials" below) and drives its real "post an ad" UI. See "Automation: Playwright-based posting" below for what's actually automated so far and what's still manual. The user finishes and submits the ad in that window and then closes it. `/api/post-job` only replies once the window is closed.
   - **`off`**: the button is disabled with a note, and `/api/post-job` answers `POST_DISABLED`.

   Either way, with several locations the form then moves on to the next one (see "Domain: multi-location job postings").

There is no database — `sessionStorage` is the only state between the two pages (plus the app-login session cookies, see "Auth: app login").

## Auth: app login (ikman.lk account, persistent session)

Users log into the app itself with their ikman.lk email + password. This follows `EMAIL_AUTH_IMPLEMENTATION_SPEC.md` (a spec copied from Saltside's `web-pwa`, the ikman.lk frontend — not checked into this repo), with one deliberate deviation: the spec has a protected home page and a separate `/{locale}/users/login` page, but here **the home page `/` is public and *is* the login page** — login happens in a popup on it. So "redirect to login" always means `/?redirect-url=<path>`, which opens the popup automatically. No locale routing either; `Accept-Language` is always `en`.

- **Session = cookie.** `sessionToken` (the gateway's bearer token) and `__user` (account id) cookies, `Path=/`, 30-day `Max-Age` fixed at login (not sliding), `SameSite=Lax`, **not HttpOnly** (browser JS reads `sessionToken` to send `Authorization: Bearer`), `Secure` only when the request was actually HTTPS (`lib/auth/server.ts`'s `isHttps` — a Secure cookie over plain-HTTP `next start` would silently not persist). A non-empty `sessionToken` alone means "logged in". It's validated lazily: nothing checks it before rendering, and a dead token is only discovered when an authenticated call gets a 401.
- **BFF routes** (`app/api/auth/*`) forward to the Saltside API gateway at `API_GATEWAY_URL` (env var, optional, defaults to `https://api.ikman.lk` — the spec's example value, so set it if that turns out wrong): `POST /api/auth/sessions` → `POST /v1/sessions` (never with `Authorization`; on 200 sets both cookies), `GET /api/auth/account` → `GET /v1/account` (forwards `Authorization`; on 401 also clears the cookies), `POST /api/auth/logout` (no upstream call — the token isn't revoked, just forgotten; clears cookies, 204). The spec calls these `/data/*`; they're under `/api/auth/*` here to match this app's `app/api/` convention. Upstream headers: `Content-Type`, `Accept-Language`, `Application-Name: web`, `X-Forwarded-For` (client IP if known). 30 s timeout. Never log the password or token.
- **This is a different endpoint from `/api/ikman-auth`** (the now-unused job-form "Authenticate" pre-check, which hits `https://ikman.lk/data/sessions`, the web-pwa BFF). The app login's token is also what "Post Job" reuses to post as the logged-in user — see "Domain: Ikman.lk login credentials".
- **Page protection:** `proxy.ts` redirects requests for `/upload/*` and `/job-form/*` without a `sessionToken` cookie to `/?redirect-url=<path>`. On `/`, the server component (`app/page.tsx`) redirects an already-logged-in user who arrives with `redirect-url` straight to it (`safeRedirect`'d) instead of showing the popup. The proxy doesn't cover API routes. `/api/extract` and `/api/post-job` check the session themselves: no `sessionToken` cookie → 401, and the token is verified with the gateway's `GET /v1/account` (`verifySessionToken`). A 401 (expired/revoked) or 400 (malformed, e.g. a made-up cookie — checked live on the deployment) counts as a dead session (`isRejectedSession`), which also clears the cookies. Any other failure (5xx, network) is logged and let through. `/api/extract` does this because every call spends the AI key's quota.
- **Login popup** (`app/components/LoginModal.tsx`): a native `<dialog>` (`showModal()` gives focus trapping, Esc to close and the backdrop), mounted only while open so each open starts fresh. It closes on Esc, the X button, or a click that starts and ends on the backdrop. Its layout copies ikman.lk's own login popup: an intro + benefits column (hidden below `md`) and the form. Validation is client-side: empty email/password → "You must fill out this field." (shown after a submit attempt), malformed email → "Please enter a valid email address." (`lib/email.ts`'s `isValidEmail`, shown on submit or once the field is left with a value). The Login button looks faded while the form is invalid, like ikman's, but stays clickable so an empty submit shows the errors. Login failure with 400/401/403/422 → "Invalid email or password." Anything else (5xx, timeout, a 404 from a wrong `API_GATEWAY_URL`) → "Something went wrong." The email is kept and the password cleared. On success: `window.location.replace(safeRedirect(redirect-url, "/upload"))`. That's a full load so the proxy sees the new cookie, and a replace so Back doesn't land on the popup again.
- **401 handling:** `lib/auth/api.ts`'s `authFetch` is for every authenticated browser call. On 401 it clears the cookies and redirects to `/?redirect-url=<current page>`. Don't use it for the login call itself, where a 401 just means wrong credentials. Currently its only caller is `fetchAccount`, which `AccountMenu` calls on mount to show the account name. That call doesn't block rendering. The upload page's multipart `/api/extract` call uses plain `fetch` (`authFetch` sends JSON headers to `/api/auth/*`) and calls the same exported `handleUnauthorized()` on a 401, so the user logs in again and comes back to `/upload` (the chosen file is lost).
- `safeRedirect` only allows same-origin relative paths (rejects `//…` and `/\…`) — always pass `redirect-url` through it before navigating.
- Logout (`LogoutButton`) is in the home page header (inside `AccountMenu`) and the `/upload` and `/job-form` headers (next to a Home link; both icon-only below `sm`). Logging out from the job form drops the unsaved form edits. Neither page shows the account name.

## Domain: job category / job role taxonomy

Ikman-style job listings must have a job category, and (usually) a job role that belongs to that category — it's a fixed two-level hierarchy, not free text.

- **Source of truth:** `data/job-categories.json` — an array of `{ category: string, roles: string[] }`. `roles` is `[]` for categories that have no distinct sub-roles (e.g. "Cashier", "Cleaner", "Supervisor"); in that case the category name itself is the only valid role.
- **Helpers:** `lib/jobCategories.ts` exports `getCategoryNames()`, `getRolesForCategory(category)`, `matchCategory(input)`, `matchRole(category, input)`, `findCategoryByRole(role)`. These do case-insensitive matching and return the canonical spelling from the JSON.
- **To add/rename/remove a category or role:** edit `data/job-categories.json` only. Both the extraction prompt (`lib/jobExtraction.ts`) and the form dropdowns (`app/job-form/page.tsx`) read this file live — nothing else needs to change.
- **It mirrors ikman.lk's live post-ad forms** (synced Oct 2026): category names are the live job categories under `GET {API_GATEWAY_URL}/v1/categories`'s `jobs` category (deactivated duplicates skipped), and each category's roles are the `item_type` labels of `GET /v1/post_ad_forms/{categoryId}/{townId}/for_sale` (whitespace collapsed); `roles: []` exactly where ikman.lk's form has no Role field. "Overseas Jobs" is left out, since its form requires a country and an SLBFE licence number we don't collect. Both posting methods pick options by these labels, so a spelling that drifts from ikman.lk's breaks posting in that category. Re-sync from those two endpoints rather than hand-editing.
- **Rule for any code touching category/role:** never hardcode a category or role list inline anywhere else in the app — always go through `lib/jobCategories.ts` / `data/job-categories.json`, and always validate/normalize a category or role against this taxonomy before trusting it (an AI extraction or a stale cached value can contain a value outside the list — treat a non-match as "unknown", not an error).
- In the UI, the Job Role `<select>` is populated from the currently selected Job Category and is disabled/empty until a category is chosen.

## Domain: locations (ikman.lk district ⇄ town tree)

Location is two cascading levels: **L1 = district** (Sri Lanka's 25 districts) and **L2 = town/area** within it. The list is **ikman.lk's own location data**, fetched from its backend, not a hand-maintained file. That way the names the form shows are exactly ikman.lk's own, and each maps to the ikman.lk location id the Playwright automation selects in the posting UI (see "Automation: Playwright-based posting"). This replaced the old `data/sri-lanka-locations.json` (140 "popular" towns, some names differing from ikman.lk's).

- **Source:** `GET {API_GATEWAY_URL}/v1/locations` with `Accept-Language: en` (the "Option A: raw backend" route of `location-tree-guide.md`, a guide ported from Saltside's `web-pwa`; not checked into this repo). It returns a flat array of nodes (`id`, `name`, `slug`, `geo_region`, `children: number[]`, optional `deactivated`/`old_slugs`, large `geography` polygons) plus `groups` (the display order of the top level), and a `version` response header. Checked live (Oct 2026): 25 districts / 306 towns.
- **Building the tree** (`lib/locations/tree.ts` `buildLocationTree`, a port of web-pwa's `tree_utils.js`): adds `link` (`/ads/{englishSlug}`), drops `geography`, adds a synthetic root `{ id: -1, name: "Sri Lanka", slug: "sri-lanka" }` whose children are every node that has children, keys nodes by id, and sets `parentId` by a depth-first walk from the root (root `parentId: null`, districts `-1`). Unreachable nodes are dropped, dangling child ids and cycles are skipped. After the JSON round trip to the browser the map's keys are strings; indexing with numbers still works.
- **Lookups** (`lib/locations/lookup.ts`, all by **name**, case/whitespace-insensitive, deactivated nodes excluded): `getDistricts` (in `groups` order, falling back to the root's children), `getTowns(data, districtName)`, `findDistrict`, `findTown(data, name, districtName?)`, `getDistrictTown` (the town that stands for the district itself: same name, or "<District> City" — 24 of 25 districts have one; **Colombo doesn't**, its areas are "Colombo 1"–"Colombo 15" plus suburbs), `getLocationTaxonomy` (compact `{district, towns}[]` for the prompt).
- **`resolveLocation(data, {district, town})`** maps a loose pair (from extraction, or a stale cached form value) onto exact names. A known town wins and brings its parent district along (the given district only disambiguates same-named towns, and is overridden if it disagrees). A district with no town selects the district plus `getDistrictTown` (e.g. "Kandy" → Kandy / Kandy City; Colombo → Colombo / blank). A town ikman.lk doesn't list keeps the district with a blank town. Names in the wrong field are still recognized. Anything unknown → `null`, the same "unknown, not an error" treatment as category/role.
- **Loading:** server-side `getLocationData()` (`lib/locations/server.ts`) fetches once, caches in memory for 24 h (a failed refresh keeps serving the last good copy) and logs `[locations] loaded N districts / M towns (version …) in X ms`. The browser gets it from `GET /api/locations` (`Cache-Control: public, max-age=86400`; 502 + `{ error }` if the backend is unreachable) via `loadLocations()` (one shared request per page load) / the `useLocations()` hook (`status: loading | ready | error`, `retry()`).
- **Extraction:** `/api/extract` passes the tree to `buildExtractionSystemPrompt()` (so the model picks from ikman.lk's names, and is told to leave `town` null when the poster names only a district) and to `toJobDetails()`, which runs every extracted location through `resolveLocation` and dedupes. If the tree can't be loaded, extraction still runs, with no location list and `locations: []`, so the user picks the location by hand. A warning is logged.
- **Form:** `JobLocationForm` fills the District `<select>` from `getDistricts` and the Town `<select>` from `getTowns(selected district)`. Town is disabled until a district is chosen; both are disabled while loading. On a load error the district select shows "Districts unavailable" with a "Try again" link, and the error goes to the console. Changing district keeps the town only if the new district has it. Choosing a district by hand does **not** auto-select its "City" town; only extraction does. On load, `app/job-form/page.tsx` re-runs `resolveLocation` over every tab once the tree arrives, so a stale `sessionStorage` value can't leave a selection that doesn't exist.
- **Rule for any code touching district/town:** never hardcode a district or town list — always go through `lib/locations`, and validate/normalize with `resolveLocation`/`findDistrict`/`findTown` before trusting a value. The form stores **names**. The Playwright automation turns them back into ikman.lk location ids (`LocationItem.id`) to click the picker's options by test id. The same ids would also serve the dormant direct-API path (`data/ikman-location-map.json`) if it's ever revived.

## Domain: job type

Job Type is a fixed 5-value enum (not a taxonomy needing future growth), sourced once from `lib/jobTypes.ts`: `JOB_TYPES = ["Full Time", "Part Time", "Contractual", "Internship", "Temporary"]`, plus `matchJobType(input)` for the same case-insensitive-match-or-null normalization used everywhere else. Rendered as a plain `<select>` (via `JobLocationForm`'s generic `type: "select"` field support in `ABOUT_JOB_FIELDS`) — no cascading dependency, unlike category/role or district/town. An unmatched/unmentioned value normalizes to `null`/blank (green, needs manual selection), never a free-text value outside these 5.

## Domain: required education

Required Education is the same kind of fixed enum as Job Type, sourced from `lib/education.ts`: `EDUCATION_LEVELS = ["Ordinary Level", "Advanced Level", "Certificate", "Diploma", "Higher Diploma", "Degree", "Masters", "Doctorate", "Skilled Apprentice"]`, plus `matchEducation(input)`. Also a plain `<select>` via `ABOUT_JOB_FIELDS`'s generic `type: "select"` support. The extraction prompt explicitly maps common poster wording/abbreviations to these values (e.g. "O/L" -> "Ordinary Level", "Bachelor's/BSc" -> "Degree", "PhD" -> "Doctorate") rather than asking the model to invent its own phrasing — anything that doesn't map cleanly normalizes to `null`/blank.

## Domain: job description (language templates)

The ad's Description is **not** free text written by the model. It's one of six fixed templates in `lib/jobDescription.ts`: English, Sinhala or Tamil, each in a "general" or a "✪ 𝐖𝐀𝐋𝐊 - 𝐈𝐍 𝐈𝐍𝐓𝐄𝐑𝐕𝐈𝐄𝐖𝐒 ✪" variant. They were supplied by the ops team, with 𝐌𝐚𝐭𝐡-𝐛𝐨𝐥𝐝/𝓈𝒸𝓇𝒾𝓅𝓉 Unicode headings, emojis, `【~】✪ 🔹` bullets (Tamil: `【~】✪`) and standard benefits/how-to-apply sentences. That fixed text lives in the code verbatim, so the model can't reword it.

- **Extraction** returns `descriptionDetails` instead (`EXTRACTION_SCHEMA`): `language` (the poster's main language), `walkInInterview`, `position`, `qualifications`/`requirements`/`responsibilities`/`benefits` lists, `interviewDate`/`Time`/`Location`/`Address`, `contactPhone`, `email`, `address`. The Web line reuses `employerWebsite`. Absent values are `""`/`[]`, not `null`, to keep the schema's union (`anyOf`) count down. `toJobDetails` renders them with `buildJobDescription` into `JobDetails.description`, a plain string as before. The form and the Playwright fill are unchanged.
- **Language:** `descriptionDetails` content is written in the template's language. Sinhala/Tamil posters keep their own wording; an English poster gets any Sinhala/Tamil parts translated. This is the one exception to "translate everything to English". Every other field, including `employerName`, stays English.
- **Rendering rules:** a section or line with no content is left out, never shown as an empty placeholder. Exceptions are the position line (it falls back to `jobRole`/`posterTitle`) and the fixed boilerplate. Poster benefits are added after the template's standard benefits sentence. Templates with a single requirements section get qualifications + requirements merged; only English walk-in shows "Qualifications" separately. The English walk-in template has no Responsibilities section, so they're dropped there. Sinhala walk-in has one interview-place line (venue + address joined) and no contact block. Tamil general has no standard benefits sentence, so it borrows the walk-in one when the poster lists no benefits. Blank lines between sections are normalized (the supplied templates were inconsistent).
- **Editing a template:** change the matching function in `lib/jobDescription.ts`. Sinhala conjuncts (ප්‍ර, ක්‍ෂ) contain a zero-width joiner (U+200D), so make sure an edit keeps it.

## Domain: salary range

Salary is captured as a range, not one free-text field: `JobDetails.salaryFrom` / `salaryTo` (`types/job.ts`, both `string | null`). A stated range splits across both; a single fixed figure (not a range) goes in `salaryFrom` only, `salaryTo` stays `null` — never the reverse. Rendered as two side-by-side text inputs via `JobLocationForm`'s generic `type: "range"` field support (`ABOUT_JOB_FIELDS`, `rangeIds: [fromId, toId]`) — no fixed value list here (unlike Job Type/Education), just free text, since salary figures/currency vary too much to enumerate.

## Domain: application deadline (date picker)

`applicationDeadline` (`types/job.ts`) is stored as an ISO `YYYY-MM-DD` string or `null` — the exact format a native `<input type="date">` requires to display a value and open the browser's calendar picker. `lib/date.ts` exports `isIsoDate(value)`, used both server-side (`lib/jobExtraction.ts`'s `toJobDetails`, to null out anything the model returns that isn't already exact ISO) and client-side (`app/job-form/page.tsx`, same defensive check on load). The extraction request is given today's date per request (in the user message, next to the image — the system prompt stays static so it can be prompt-cached) so it can resolve relative deadlines ("within 2 weeks") or a day/month stated without a year; if it can't resolve a full date, it must return `null` rather than guess. Rendered via `JobLocationForm`'s `type: "date"` field support (`ABOUT_JOB_FIELDS`) — a plain native date input, no custom calendar widget.

## Domain: application phone number

`applicationPhone` (`types/job.ts`, `string | null`) is the phone number applicants should call — unlike every other field, it is **never extracted from the poster**: `lib/jobExtraction.ts`'s `toJobDetails` always sets it to `null`, and the extraction prompt doesn't ask the model for it at all. It's always manual entry, which is also why it's never given special-case normalization the way jobType/education/date are — there's no AI value to normalize, just a blank field that's always green until filled in.

- Rendered via `JobLocationForm`'s `type: "tel"` field support (`ABOUT_JOB_FIELDS`), one text input per location tab (same per-location independence as employer name/website — see multi-location section below).
- **Validation:** `lib/phone.ts` exports `isValidSriLankanPhone(value)` — accepts local format (`0` + 9 digits, e.g. `0771234567`) or international format (`+94` + 9 digits, e.g. `+94771234567`), first digit after the prefix non-zero; spaces/dashes are stripped before matching. This is a general format check (mobile + landline), not carrier/prefix-specific.
- A non-empty value that fails validation shows a red border + inline error message (`JobLocationForm.tsx`) instead of the green "needs manual entry" style — `fieldClasses(id, invalid)` takes an `invalid` override for this. Validation is advisory only — it doesn't block form submission.
- **When posting** ("Post Job"), ikman.lk's "receive applications by Phone" option is always used. A blank field falls back to the logged-in ikman.lk account's own number, and with no number at all posting is refused (`POST_PHONE_REQUIRED`). See "Main job-post form field mapping".

## Domain: Ikman.lk login credentials

**"Post Job" posts as the user logged into this app, without logging in again.** The app login (see "Auth: app login") already holds the user's ikman.lk session token, from the same `POST /v1/sessions` ikman.lk's own web app uses. ikman.lk's web app (web-pwa) treats a `sessionToken` cookie as "logged in", so the automation's browser reuses that token instead of typing an email/password.

- **`/api/post-job`** reads the app's `sessionToken` and `__user` cookies from the request. With no token → `POST_NOT_LOGGED_IN` (401). It then checks the token with `lib/auth/server.ts`'s `verifySessionToken()` (gateway `GET /v1/account`). A 401 or 400 (`isRejectedSession`) → `POST_SESSION_EXPIRED` (401, and the app's session cookies are cleared, like any other 401). Success logs `[post-job] posting as "<name>" (ikman.lk account <id>)`; never the token. A network/other failure of this check is logged and posting continues, since it's only a pre-check.
- **`postJob(job, { session: { token, accountId } })`** opens a fresh browser context and `addCookies()` the token and account id as ikman.lk's own cookies (`siteConfig.sessionCookies`: `sessionToken`, `__user`; host-only on `baseUrl`'s origin) before the first `page.goto`, then skips the recorded login-form steps. Once the header has rendered ("POST YOUR AD" visible), a visible "Login" link means ikman.lk didn't accept the session → `PostJobError("POST_AUTH_FAILED")` (502), rather than continuing logged out. **Not yet confirmed against a live run.** If ikman.lk ever needs more than these cookies (e.g. its own server-side `sid` session), this check is where it shows up.
- For those three codes the job form's error banner adds a **"Log in again"** button. It clears the app session (otherwise the home page sees the old cookie and skips the login popup), then goes to `/?redirect-url=/job-form`. After login the user returns to the job form, which reloads the *originally extracted* data from `sessionStorage`; edits made on the form are lost, since `jobForms` isn't persisted.
- The job form no longer has its own "Ikman.lk Login" section (it was removed on request), and nothing collects or stores an ikman.lk password. The `.env.local` account (`JOB_SITE_USERNAME`/`PASSWORD`) is only for `npm run automate:post-job`.
- `IkmanCredentials` (`types/auth.ts`), `/api/ikman-auth` and `lib/ikman.ts`'s `authenticateIkman` stay in place but are unused by the UI. `IkmanSession` is now what `postJob` receives.

## Domain: posting to ikman.lk (direct API, dormant)

**Not currently wired to the UI** — "Post Job" drives the Playwright path below instead. Kept in place, not deleted, in case a direct-API path is wanted again instead of/alongside browser automation.

`lib/ikman.ts`'s `postIkmanListing(job, credentials, session)` POSTs directly to ikman.lk's real `POST https://ikman.lk/data/post_listings` with `Authorization: Bearer <session.token>` — reverse-engineered from one captured browser request while posting a job ad, so several parts are best-effort until confirmed against a real response:

- **`buildAdPayload(job, credentials)`** turns one location tab's field map into `{ ad: { category, location, ai_generated: false, type: "for_sale", images: [], extra_images: [], contact_card, properties }, account_phone_numbers: false }`:
  - `category`/`location` are ikman.lk's own numeric ids, resolved via `lib/ikmanMapping.ts`'s `getIkmanCategoryId(job.jobCategory)` / `getIkmanLocationId(job.district, job.town)` from `data/ikman-category-map.json` (`{ "Category Name": id }`) / `data/ikman-location-map.json` (`{ "District": id }` or `{ "District|Town": id }`, town-specific entry tried first). **Both maps start empty** — there's no way to derive ikman.lk's internal ids from our taxonomy names, so `buildAdPayload` returns a `{ success: false, error }` (surfaced in the "Post Job" error banner) for any category/location not yet added to these maps, rather than guessing.
  - `properties` enum values (`item_type`, `employment`, `min_qualification`) use `slugify()` — lowercased, spaces/punctuation to `_` — on our own taxonomy labels (e.g. "Full Time" -> "full_time"). This matched the one sample payload exactly, on the theory that this app's `jobTypes`/`education`/category-role taxonomy was originally transcribed from ikman.lk's own posting form — **not independently confirmed for every value**, just the ones seen so far.
  - `contact_card.email` is `credentials.email` (the logged-in account); `contact_card.phone_numbers` and the `apply_via_multi` property's `phones` both reuse `applicationPhone` — the sample request had two *different* numbers in these two spots, so this may need a distinct "employer contact phone" field later if they're meant to differ.
  - `type: "for_sale"` is hardcoded from the one sample seen — unconfirmed whether job ads ever use a different `type` value.
  - **Not sent at all yet** (no confirmed ikman.lk property `key` for these): `salaryFrom`/`salaryTo`, `applicationDeadline`. `requiredExperience` (free text, e.g. "2+ years") is best-effort parsed to an integer via the first number found in the string (`experience` property), and omitted entirely if none is found — never guessed.
  - `ad-form-version` (a frontend build-hash header seen on the sample request) is **not sent** — no reliable source for its current value from server-side code; if ikman.lk starts rejecting requests, this is the first thing to check.
- `postIkmanListing` sends only `Content-Type`, `Accept`, `Authorization`, and `application-name: web` as headers — browser-fingerprint headers from the sample (`user-agent`, `sec-ch-ua*`, `origin`, `referer`, `device-type`, `dnt`) are deliberately not replicated (this is a server-to-server call, not a browser request).

## Posting: browser extension (`POST_JOB_METHOD=extension`)

The deployed app can't run the Playwright flow (no browser or screen on Vercel), so "Post Job" hands the job to a Chrome extension that fills ikman.lk's post-ad form **in the user's own browser**, under the user's own ikman.lk login. Nothing is submitted for the user.

- **Hand-off** (`lib/postAdHandoff.ts`, called by `/api/post-job` after the usual session check and `withApplicationPhone` fallback): `url` is `https://ikman.lk/en/post-ad/details?type=for_sale&category={id}&location={townId}` — the URL ikman.lk's own post-ad page moves to once a category and town are picked, so the category/location pickers are skipped entirely. Category ids come from `GET /v1/categories` (live children of the `jobs` category, matched case/whitespace-insensitively, cached 24 h), town ids from the location tree. If either id is unknown, it falls back to `https://ikman.lk/en/post-ad` (the user picks both, the extension fills the form once it appears). `fields` are pre-normalized: experience and salary reduced to digits, a single salary copied into `salaryTo` (ikman.lk drops a salary range with one end), phone in local `07…` format.
- **Page ⇄ extension** (`lib/extension.ts` ⇄ `extension/app-bridge.js`, via `window.postMessage`; sources `job-poster-analyzer` / `ikman-job-poster-extension`): Post Job first pings (1 s timeout); no answer → `POST_EXTENSION_MISSING`, whose banner links to `/extension`. Then `post-job` with the hand-off (10 s timeout); no answer or `ok: false` (e.g. "Extension context invalidated" after an extension update, until the page is reloaded) → `POST_EXTENSION_FAILED`. On success the form shows "Opened … on ikman.lk in a new tab" and moves to the next location.
- **`background.js`** opens a tab at `about:blank`, stores the hand-off in `chrome.storage.session` under that tab id, then navigates it to the URL (so the page can never ask before the job is stored), and serves it to that tab's content script. Other ikman.lk tabs get nothing and are left alone.
- **`ikman-fill.js`** polls (up to 15 min, since ikman.lk is a single-page app and may route through its login) until it's on `/post-ad/details`. **ikman.lk's login redirect keeps the category but replaces the town** (seen live: `location=1549` came back as `2196`), so if the URL's `category`/`location` differ from the hand-off's, it `location.replace`s the hand-off URL (at most twice, counted in the stored job). Then it fills the form and shows a dismissible banner: "check every field, then click Post ad", the deadline to pick, and any value it couldn't place.
- **ikman.lk's form is Preact** (DOM nodes carry Preact's `l` listener map, not React props) with Downshift dropdowns. Text fields are matched by `name` (`title`, `description`, `experience`, `From`, `To`, `company_name`, `company_website`); dropdowns by their toggle `button[aria-label="open menu"][name=item_type|employment|min_qualification]`, then the `[role=option]` whose text matches (case/whitespace-insensitive); applications-by-phone by clicking the `label[for]` that starts with "Phone (up to 3)", then the first `input[placeholder="Enter phone number"]` once it's enabled. Values are set with the native value setter + an `input` event (Preact's `onChange`), focusing first and **blurring only after ~100 ms**: blurring at once re-saved the field's previous (empty) value, and the field came back blank. The ad's contact phone (verified account numbers) is already filled in by ikman.lk.
- **Not filled:** the application deadline. ikman.lk's `#input_deadline` is read-only behind a calendar widget, so the banner tells the user which date to pick. Images aren't touched either.
- **Install:** `/extension` (public) explains loading it unpacked (Developer mode → Load unpacked); `/extension/download` zips `extension/` per request into one `ikman-job-poster-extension/` folder (`next.config.ts`'s `outputFileTracingIncludes` ships the files with that route). `app-bridge.js` only runs on `https://job-poster-analyzer.vercel.app/*` and `http://localhost/*` (any port) — **a new production domain must be added to `manifest.json`**, and users must reinstall.
- **Verified (Oct 2026)** with Playwright driving Chromium with the unpacked extension: app login → job form → Post Job → new ikman.lk tab, logged out → ikman.lk login in that tab → the extension reopened the right category/town and filled every field (role, title, description, job type, phone, experience, education, salary, employer, website), with no form errors — against `next start` locally and against the Vercel production deploy. "Post ad" was never clicked.

## Automation: Playwright-based posting

`automation/postJob.ts`'s `postJob(job, credentials?)` drives a real (non-headless by default) Playwright browser against ikman.lk itself — this is what `app/api/post-job/route.ts` calls, and what "Post Job" actually triggers. Its steps and selectors were captured by recording a real session with `npx playwright codegen https://ikman.lk/en` (log in, click through to the job form) rather than guessed, since ikman.lk's login and category/district/town pickers are accessible-role based (buttons/links/textboxes matched by their visible name via `page.getByRole(...)`), not plain CSS ids/classes.

- **Selectors/labels live in `automation/config/site.config.ts`** (`login.*`, `postAdButtonName`, `postJobEntryButtonName`) — same "one source of truth, never hardcode inline elsewhere" rule as the taxonomies above. `automation/config/browser.config.ts` controls engine/headless/slowMo/timeouts separately.
- **Current recorded flow, in order:** go to `baseUrl` → log in (from the job form: nothing to click, the session cookies are already set and the automation only checks the header shows no "Login" link; from the CLI: click "Login" link → click "Continue with Email" → fill Email/Password textboxes → click "Login" button) → click "POST YOUR AD" → click "Post a job in Sri Lanka" → click a button named after `job.jobCategory` → select `job.district` → select `job.town` in ikman.lk's location picker. The category button is labeled with the taxonomy value itself, so it's clicked by `page.getByRole("button", { name: job.jobCategory, exact: true })` (**`exact: true`** — a substring match can hit two buttons, which Playwright rejects as a strict-mode violation).
- **District/town are selected in ikman.lk's location selector by `data-testid` hooks and location ids** (`automation/locationSelector.ts`, following Saltside's "Selecting a location with web automation" guide, `location-selector-automation.md`; not checked into this repo). The Post Ad selector is the shared modal also used on the Home page. It is **not** the search-results page's multi-select location filter, which shares the `location-selector-` prefix but has different hooks (`…-option-button`, checkboxes).
  - Hooks live in `siteConfig.locationPicker`: `location-selector-button` (trigger; `data-disabled="true"` when disabled), `location-selector-content` (ready when visible), `location-selector-load-error`, `location-selector-primary-column` (districts), `location-selector-secondary-column` (one opened district's cities; its own `data-option-key` is the district id), `location-selector-option` (the clickable `<button>` itself, with `data-option-key` = ikman.lk location id, `data-option-label` = name, `data-selected`), plus footer `location-selector-apply`/`-loading` on pages that have one.
  - **Flow** (`selectJobLocation`): wait for the selector content or the trigger. If the content didn't open on its own (after a 3 s grace period, so we never click the trigger behind an auto-opening modal), click the trigger unless it's disabled. Then wait for `content` (or `load-error`), and run `pickCity`:
    - click the district **inside the primary column** — this only *opens* it;
    - wait for `secondary-column[data-option-key=<districtId>]`;
    - click the town inside that column;
    - click "Show" if a footer exists;
    - wait for the dialog to close.

    Always scope options to a column, since a district and a city can share a name. The flow works on both layouts (desktop ≥ 800px shows two columns; mobile swaps the district list for the city list). Playwright's default 1280px viewport gives desktop.
  - **Ids:** `resolveLocationChoice()` looks up the job's district/town in our location tree (`findDistrict`/`findTown`, server-side `getLocationData()`, which works from the CLI too). Options are matched by `data-option-key` (language-independent). If the tree can't be loaded, or doesn't have the names, it falls back to matching `data-option-label` (English pages only) and logs a warning.
  - **Post Ad accepts cities only** (no "All of Sri Lanka" or "All ads in <District>"), so `postJob` rejects a job without both district and town up front, before launching a browser → `POST_LOCATION_REQUIRED` (400). Any stall (selector never opens, load error, option never appears, dialog never closes) → `POST_LOCATION_NOT_FOUND`, whose technical text says which step and which ids.
  - **Verified (Oct 2026)** by running the real `pickCity` against the same component on ikman.lk's Home page (opened there via `.gtm-home-location-picker-click`, the Home page's only trigger hook): Colombo `1506` → Nugegoda `1549` (desktop), Kandy `1636` → Kandy City `1644` (390px mobile layout), and Galle → Hikkaduwa by label. Each time the dialog closed and the trigger showed the town. The Post Ad opening step (`location-selector-button`) sits behind login and wasn't exercised. Why the old approach failed: clicking buttons by exact name, with headings recorded from an older UI.
- **These three steps are order-dependent, not independent:** ikman.lk only reveals the location selector after a category is picked. Since each step is separately guarded (`if (job.jobCategory)`, `if (job.district)`, `if (job.town)`), a job missing `jobCategory` skips straight to trying to click a district button on a page that never advanced past category selection — this looks like "the district/town click is broken" but is actually just missing upstream data. `automation/run.ts`'s `sampleJob` sets all three (`"Accounting & Finance"` / `"Colombo"` / `"Nugegoda"`) to values confirmed against a real recorded session for exactly this reason.
- **Each location step waits for the next element to be ready first** (the selector content, then the district's secondary column). Without a wait like this, a click can land on a stale/pre-render element from the screen that's mid-transition-out: Playwright reports the click as successful, but the location picker never actually advances, and the automation silently stalls with no error. This was originally diagnosed by re-running the steps standalone with explicit pauses, which succeeded. It used to be handled by waiting for recorded screen headings ("Select City or Division" / "Select a local area within …"); waiting on the guide's test ids replaced that and no longer depends on heading text. Related gotcha when testing on a freshly loaded page: a trigger click before React hydrates (or, on the Home page, while its text still ends in " ...") does nothing.
- `postJob(job, login)` logs in, in priority order, with `login.session` (the job form's path: cookie injection, no login form), `login.credentials` (typed into the login form; nothing passes these today), or `siteConfig.auth`'s `.env.local` credentials (`JOB_SITE_USERNAME`/`JOB_SITE_PASSWORD`/`JOB_SITE_LOGIN_REQUIRED`) — used only by `npm run automate:post-job` (`automation/run.ts`), which has no app session. With none of them, it throws `POST_CONFIG` before opening the login flow.
- **`automation/run.ts` loads `.env.local` via a dynamic `import("./postJob")` after `process.loadEnvFile`, not a static top-of-file import.** This project has no `"type": "module"` in `package.json`, so there's no top-level `await` to reach for either. A static import of `postJob.ts` (which pulls in `site.config.ts`, reading `JOB_SITE_USERNAME`/`PASSWORD`/`LOGIN_REQUIRED` from `process.env` at module-eval time) would be hoisted and evaluated before `run.ts`'s own `loadEnvFile` call ever runs, silently leaving those env vars unset — this previously made the CLI test entry point unable to authenticate via `.env.local` at all unless those vars happened to already be exported in the shell.
- **`postJob` leaves the browser open**, on success or on error. This is deliberate: the final submit button (and a few fields) aren't automated, so the user finishes the ad by hand, and after a failure the window shows exactly where the flow stopped. The browser process is only closed once the user has closed its window.
- **Detecting the window being closed** (`whenWindowClosed` in `postJob.ts`): Playwright launches Chromium with `--no-startup-window`, so the browser process outlives its last window and `"disconnected"` does **not** fire when the user closes the window. Verified: closing the only tab from the browser side fires the page's `close` event at once, and the browser stays connected. So "window closed" = every page in the context has closed (or the browser disconnected). A popup tab closing while the main one is open doesn't count. When it happens, the leftover browser process is closed.
- `postJob` resolves with `{ windowClosed }` (a promise that never rejects) once the automated steps are done. `/api/post-job` awaits it before replying `{ success: true }`, so a "Post Job" request stays open while the user finishes the ad, which can take minutes. Node's server has no response timeout for this; a proxy in front of it would need a long one. The CLI (`npm run automate:post-job`) ignores it, and its process exits once the window is closed.
- Closing the window **mid-flow** is an expected event, not just an edge case: `postJob` races its step sequence against the same window-closed signal (`Promise.race`), so a manual close rejects promptly with `POST_BROWSER_CLOSED` instead of leaving `/api/post-job` (and the "Post Job" button) hanging on whatever Playwright action was in flight.

### Posting errors

"Post Job" failures follow the same pattern as extraction: the job form shows only a generic message from `POST_JOB_ERROR_MESSAGES` (`lib/errorMessages.ts`) plus "Error code: …". The technical detail goes to the browser console (`[post-job] ✖ CODE: technical`, plus a details object) and the server terminal (`[post-job] ✖ CODE → HTTP status` block plus the full error with Playwright's call log).

- `postJob` throws `PostJobError` (`automation/errors.ts`) for the cases it knows: `POST_CONFIG` (no `JOB_SITE_URL`, no login credentials) and `POST_BROWSER_CLOSED` (the window-closed race).
- `classifyPostJobError()` maps everything else. Playwright's `errors.TimeoutError` → `POST_TIMEOUT`. Since Playwright doesn't type its other errors, they're recognized from the message text: "…has been closed"/"Target closed" → `POST_BROWSER_CLOSED` (e.g. the window was closed mid-`page.goto`); `browserType.launch`/"Executable doesn't exist" → `POST_BROWSER_LAUNCH_FAILED` (run `npx playwright install`); `net::ERR_*` → `POST_NAVIGATION_FAILED`; anything else → `POST_FAILED`. It also strips Playwright's ANSI color codes from the technical text.
- `POST_PHONE_REQUIRED` (no phone number on the form or the account; see the phone bullet under "Main job-post form field mapping").
- `POST_LOCATION_REQUIRED` (no district or town; ikman.lk's Post Ad needs a town) and `POST_LOCATION_NOT_FOUND` (the location selector stalled) — see the location-selection bullet under "Automation".
- Extension method, browser-side: `POST_EXTENSION_MISSING` (no answer to the ping; the banner links to `/extension`) and `POST_EXTENSION_FAILED` (the hand-off wasn't acknowledged). See "Posting: browser extension".
- Login-related codes (`POST_NOT_LOGGED_IN`, `POST_SESSION_EXPIRED`, `POST_AUTH_FAILED`) are described under "Domain: Ikman.lk login credentials"; the banner adds a "Log in again" button for them.
- Browser-side codes: `NETWORK_ERROR` (fetch to `/api/post-job` failed), `BAD_SERVER_RESPONSE` (non-JSON reply). Bad request bodies → `POST_INVALID_REQUEST` (400). Posting switched off for the deployment → `POST_DISABLED` (501), checked before anything else.
- Response shape: `PostJobResponse` (`types/job.ts`) — `{ success: true }` or `{ success: false, error, code, details: { technical, durationMs, job: {title, category, role, district, town} } }`.

### Main job-post form field mapping

Once past the location picker, `postJob.ts` fills the rest of the form from `job` using labels/names in `siteConfig.jobForm` — verified by actually running `postJob` end-to-end and screenshotting the resulting ikman.lk page (not just checking for a thrown error, since the location-picker bug above showed a click can "succeed" without the UI actually reflecting it):

| `job` field | ikman.lk field | How it's filled |
|---|---|---|
| `jobRole` | Role | Combobox — see below |
| `posterTitle` | Title | Plain textbox |
| `description` | Description | Plain textbox (the rendered language template, see "Domain: job description") |
| `jobType` | Job type | Combobox |
| `requiredExperience` | Required work experience (years) | Spinbutton — first number regex-matched out of the free-text value (e.g. `"3 years"` → `3`); skipped entirely if no number is found, never guessed |
| `requiredEducation` | Required education | Combobox |
| `salaryFrom` / `salaryTo` | Salary per month: From / To | Spinbuttons — non-digit characters stripped (e.g. `"Rs. 10,000"` → `10000`) |
| `employerName` | Employer | Plain textbox (`exact: true` — a non-exact match also hits the "Employer Website" field) |
| `applicationPhone` (or the ikman.lk account's number) | "How do you want to receive applications?" → Phone (up to 3) | Always ticked, + phone textbox in local `07…` format — see below |

- **`jobRole`/`jobType`/`requiredEducation` are custom react-select-style comboboxes**, not native `<select>`: each is a `role=combobox` container with an inner control labeled "open menu" that has to be clicked to open the option list, then the option is clicked by its text (`selectComboboxOption()` helper in `postJob.ts`). Values are our own taxonomy labels (`lib/jobCategories.ts` roles, `lib/jobTypes.ts`, `lib/education.ts`) and matched ikman.lk's option text exactly in every case seen so far (e.g. "Ordinary Level", "Full Time") — this is why no separate id mapping is needed, same reasoning as the category/district/town buttons.
- **The "Phone (up to 3)" checkbox can't be clicked via its `role=checkbox` locator** — the actual `<input type="checkbox">` is visually hidden (`sr-only`) and its `<label>` sits on top intercepting pointer events, so `page.getByRole("checkbox", {...}).click()` times out. Clicking the label's text instead (`page.getByText(jobForm.applicationPhoneCheckboxLabel, { exact: true }).click()`) works, since a native `<label for="...">` click always toggles the checkbox it wraps. If that click doesn't leave it ticked (`isChecked()`), the checkbox is checked directly with `check({ force: true })`. This section is **required** by ikman.lk (shows "You must fill out this field." until one of its two options is picked). It was discovered by screenshotting the form after the first field-mapping pass, since it wasn't part of any earlier recording.
- **Applications are always received by "Phone"** for now (never "Email and employer dashboard"), so posting needs a number. The step used to be skipped when the form's phone was empty, which left this section unticked and the run stuck. `/api/post-job` (`withApplicationPhone`) uses the form's **Applications Receive Phone Number**. If that's blank, it falls back to the logged-in ikman.lk account's own number and logs that it did (not the number). It takes the first valid Sri Lankan number found by `lib/phone.ts`'s `findSriLankanPhone` across `recent_phone_numbers` from `GET /v1/account`, then the login phone number. **`recent_phone_numbers` entries are not the plain strings the login spec's sample shows.** Passing one through as-is crashed posting with `applicationPhone.trim is not a function`. So `findSriLankanPhone` accepts strings, numbers (incl. a 9-digit number missing its leading 0) and objects/arrays (any value inside, a few levels deep). When nothing is usable, it logs the entries' *shape* (types/keys, never values) for diagnosis. `UserAccount.recent_phone_numbers` is typed `unknown[]` for this reason. With neither, `postJob` throws `POST_PHONE_REQUIRED` (400) before launching a browser. The number is typed in local format via `lib/phone.ts`'s `toLocalSriLankanPhone` (spaces/dashes stripped, `+94`/`94` → `0`), into the first "Enter phone number" input, which stays disabled until the option is ticked. Not yet confirmed against a live run.
- **Not automated yet:** `employerWebsite`, `applicationDeadline` (a custom calendar widget, not a native `<input type="date">` — a recording only captured clicking a day-number button in whatever month was already showing; landing on an arbitrary target date needs a recording that also exercises month navigation), and the final "Post ad" submit button. `siteConfig.fieldSelectors` (a CSS-selector map) and `submitButtonSelector` stay available as empty placeholders for whichever of these turn out to be plain CSS-selectable once recorded.

## Domain: multi-location job postings

A single poster can advertise the same role across several branches/cities (e.g. "Cashier needed — Colombo, Kandy, Galle"). `JobDetails.locations: JobLocation[]` (`types/job.ts`, `JobLocation = { district: string | null; town: string | null }`) holds every distinct location the extraction detected — `[]` if none, one entry for the normal single-location case, multiple entries when the poster explicitly lists more than one.

- The extraction prompt (`lib/jobExtraction.ts`) asks the model for `locations` as an array of `{district, town}` objects (both chosen from ikman.lk's location list, then mapped through `resolveLocation` — see "Domain: locations" above) and is explicit that a single address should never be split into multiple entries — only genuinely separate branches/cities count.
- `app/job-form/page.tsx` turns `locations` into one flat field-map per location (`jobForms: Record<string, string>[]`), all seeded from the same extracted data except `district`/`town`. When there's more than one, a pill-style tab bar (tab label = that location's live `town` value, falling back to `district`) is rendered above the form and the currently active tab's field map is what's shown/edited.
- `app/job-form/JobLocationForm.tsx` is the single definition of what a location's form looks like — every tab renders this same component against its own slice of `jobForms`, so per-location edits (e.g. a different salary at one branch, or picking a different district/town) never leak into other tabs. Don't fork this component per-tab or duplicate its JSX inline in the page — add fields here and every tab picks it up.
- Employer info (name/website) is part of each location's field map too (per the page's current field layout), so it's independently editable per tab, not shared globally.
- **Posting each location in turn:** "Post Job" posts only the active tab. With the extension method a tab is done as soon as ikman.lk's form has been opened for it (the rest of this bullet describes the browser method). While its run is in progress (`postingTab`), the button is disabled and a status note says which location is being posted, asks the user to finish the ad in the ikman.lk window and then close it, and names the location that comes next. When `/api/post-job` replies `{ success: true }` (the window was closed), that tab gets a ✓ (`doneTabs`) and the form switches to the next tab not yet done (`nextOpenTab`, wrapping around) and scrolls to the top. Nothing moves when every tab is done, when there's only one location, or on any error, including `POST_BROWSER_CLOSED` (window closed before the automation finished). A ✓ only means the window was closed after the automation finished; it can't tell whether the user actually submitted the ad. `doneTabs` isn't persisted, so it resets on reload.
- **Poster title format:** each tab's `posterTitle` is generated client-side in `app/job-form/page.tsx` as `"{jobRole} - {town || district}"` (e.g. "Accounts Assistant - Colombo"), or just `jobRole` when that tab has no district/town. This overrides the model's own free-text title whenever jobRole matched the taxonomy; the model's original title is kept only as a fallback for the (rare) case jobRole didn't match anything. This only runs once at load time — editing jobRole/district/town afterward does not regenerate the title, so a manual edit to the Title field is never clobbered.

## AI provider layer (poster extraction)

The AI model is decoupled from the app: `app/api/extract/route.ts` and `lib/jobExtraction.ts` only use `lib/ai`'s provider-neutral API and never import an AI SDK, so the model is swapped through `.env.local`, not by editing code.

- **Selecting a provider:** `AI_PROVIDER` (`gemini` | `claude`, case-insensitive; **required** — unset/unknown is a `config` error naming the valid values) and optional `AI_MODEL` (blank = the provider's default). Each provider reads its own key (`GEMINI_API_KEY`, `ANTHROPIC_API_KEY`) and fails fast with a `config` `AIError` if it's missing. The route shows that message in the upload error banner, e.g. "The AI service isn't configured: GEMINI_API_KEY is not set."
- **Contract** (`lib/ai/types.ts`): `AIProvider.generateJson({ system, prompt, image, schema })` → parsed JSON. `system` is static (cache-friendly), `prompt` is the per-request text, `image` is base64 + media type, `schema` is a JSON Schema each provider enforces with its own structured-output mode. All provider failures are thrown as `AIError` with a neutral `kind` (`config`, `auth`, `model_not_found`, `rate_limit`, `unavailable`, `bad_request`, `refused`, `truncated`, `invalid_output`, `network`, `timeout`), a user-facing `message` that names the provider and the specific problem, and `upstream` (`UpstreamErrorInfo`: the provider's HTTP status, error code/reason, own message, request ID — never the key) for diagnostics. The route maps each kind to an HTTP status + next-step hint (`AI_ERROR_HANDLING`) and the code `AI_<KIND>`. Errors an adapter doesn't recognize are rethrown as-is and become `INTERNAL_ERROR`.
- **Adding a provider:** write `lib/ai/providers/<name>.ts` exporting a `create…Provider(model?)` that returns an `AIProvider` (map the SDK's errors to `AIError` kinds, enforce `schema` natively if the provider supports it, otherwise use `parseJsonReply` and rely on `toJobDetails`' validation), then add one line to the `PROVIDERS` registry in `lib/ai/index.ts`. Providers are imported lazily, so only the selected provider's SDK loads. Keep the shared schema to features every provider supports (nullable fields are written as `anyOf: [X, {type: "null"}]`, objects use `additionalProperties: false` + full `required`).
- **Shared limits** (`lib/uploadLimits.ts`, checked in the browser and again in the route): JPEG/PNG/WebP only (the formats every provider accepts — Gemini lacks GIF, Claude lacks HEIC), max 4 MB uploaded (under Vercel's 4.5 MB request-body limit, which also keeps it under Claude's 5 MB per-image limit, the strictest provider's); the picker itself allows up to 10 MB since the browser downscales before uploading. HEIC isn't offered by the upload picker (phones convert camera photos to JPEG when the picker doesn't list HEIC); a dragged-in HEIC gets a "convert to JPEG/PNG" error.
- **Client-side image downscaling** (`lib/image.ts`, called from `app/upload/page.tsx` right before upload): phone-camera poster photos are downscaled to a max 1600px on the long edge (JPEG, quality 0.85) before ever leaving the browser — vision-model latency (and upload time) scales with image size, and poster text stays legible well below typical raw photo resolutions. Falls back to the original file untouched if decoding fails (e.g. most browsers can't decode HEIC via `createImageBitmap`) or the image is already small enough — never blocks the upload.

### Extraction errors & logging

Every way extraction can fail has a stable `ExtractErrorCode` (`types/job.ts`), shown in the UI next to the message and used in both consoles. **The UI only ever shows the generic message for the code** (`EXTRACT_ERROR_MESSAGES` in `lib/errorMessages.ts`, e.g. "The AI service isn't set up correctly right now. Please contact the administrator."). It never shows provider messages, HTTP statuses, env var names or the model's own reason. The specific text travels as `details.technical` and is printed to the browser console and server terminal. Exception: the upload page's own pre-upload file checks keep `validateImageFile`'s specific (but non-technical) message, e.g. "GIF images aren't supported…".

| Where | Codes | What the user sees | Console |
|---|---|---|---|
| Browser, on choosing a file (`ImageUploader` → `validateImageFile`) | `FILE_NOT_IMAGE`, `UNSUPPORTED_FILE_TYPE` (incl. HEIC by type or `.heic` name), `FILE_TOO_LARGE`, `FILE_EMPTY`, `FILE_UNREADABLE` (preview `<img>` failed to decode — damaged file) | Red `ErrorAlert` on the upload page; nothing is uploaded and the user stays on the page | `console.warn("[extract] CODE: …", {name, type, size})` |
| Browser, after resizing | `FILE_TOO_LARGE` (still > 4 MB after downscaling) | Same inline alert | same |
| Browser, during the request (`app/upload/page.tsx`) | `NETWORK_ERROR` (fetch rejected; logs `navigator.onLine`), `REQUEST_TIMEOUT` (client abort after `REQUEST_TIMEOUT_MS` = 180 s), `BAD_SERVER_RESPONSE` (non-JSON reply, e.g. a proxy error page — logs HTTP status + content-type) | Job form's amber banner with message + "Error code: …" | `console.error("[extract] ✖ CODE: …", details)` |
| Server (`/api/extract`) | `NOT_LOGGED_IN` / `SESSION_EXPIRED` (401 — the upload page sends the user to log in instead of to the job form), `NO_IMAGE`, `INVALID_REQUEST` (unreadable form data), file codes again (413/415/400), `NOT_A_JOB_POSTER` (422 — the model set `error`), `AI_<KIND>` for every `AIError` kind, `INTERNAL_ERROR` | Job form banner, as above | Browser: `console.error` of the response's `details` (provider, model, `upstream`, file, `durationMs`, HTTP status). Terminal: multi-line `[extract] ✖ CODE → HTTP status after N ms` block (message, provider/model, upstream status/code/reason/message, requestId, file) — `console.warn` for 4xx, `console.error` plus the full error chain (stack + SDK error as `cause`) for 5xx |

The response body for a failure is `{ success: false, error, code, details }` (`ExtractErrorResponse`): `error` is the generic message, `details.technical` the specific one (the `AIError` message naming the provider/problem, the model's "not a poster" reason, the file problem, or `Name: message` for unexpected errors). `details` never includes the API key. The terminal block prints both (`shown :` / `detail :`). The job form reads `extractionErrorCode` from `sessionStorage` to show the code.

### Gemini (`lib/ai/providers/gemini.ts`) — the active provider

- `@google/genai` (Google's current SDK; the older `@google/generative-ai` is end-of-life and was removed), `ai.models.generateContent` with `systemInstruction`, the image as `inlineData`, `responseMimeType: "application/json"` + `responseJsonSchema`.
- **Default model `gemini-3.5-flash-lite`** — Gemini's low-latency Flash-Lite tier, recommended by Google for new projects (checked against ai.google.dev, Oct 2026: the 2.0 models are shut down, the 2.5 family is restricted to prior users). Its thinking defaults to `minimal`, the fastest level. No `thinkingLevel` is set explicitly, because other models don't all accept `minimal` (e.g. `gemini-3.8-flash` supports low/medium/high only) and an `AI_MODEL` override would 400. Model names shift quickly; check ai.google.dev/gemini-api/docs/models when changing it.
- 60 s timeout, 3 attempts (SDK default is 5). A blocked prompt or a safety-type finish reason → `refused`; `MAX_TOKENS` → `truncated`; an invalid key comes back as HTTP 400 with reason `API_KEY_INVALID` → `auth`; 408/504 or the SDK's per-attempt abort (`AbortError`) → `timeout`; a failed `fetch` (`TypeError`, with the Node error code such as `ENOTFOUND` in `upstream.reason`) → `network`. `upstreamInfo()` pulls `status`/`message`/`details[].reason` out of the JSON error body Gemini embeds in `ApiError.message`.

### Claude (`lib/ai/providers/claude.ts`) — available, not active

- `@anthropic-ai/sdk`, default model `claude-opus-5-5` at `output_config.effort: "low"` (thinking can't be turned off on this model; effort is the latency lever — raise to `"medium"` if quality drops). Structured outputs via `output_config.format`; the static system prompt is marked `cache_control: ephemeral`; server-side refusal fallback (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`) is sent only for models in `FALLBACK_MODELS`, since other models reject it. 120 s timeout, SDK retries 429/5xx/529 twice.

## Environment & running

- Node version is pinned in `.nvmrc` (currently 24.x) — `npm run lint` / `npm run build` fail with a cryptic `SyntaxError` under an older Node picked up by a stale shell. Run `nvm use` first if lint/build errors look like a parser crash rather than a real lint/type error.
- Extraction needs `AI_PROVIDER` plus that provider's key in `.env.local` (git-ignored): currently `AI_PROVIDER=gemini` + `GEMINI_API_KEY` (from aistudio.google.com/apikey). `AI_MODEL` is optional. `ANTHROPIC_API_KEY` is only needed when `AI_PROVIDER=claude`. See "AI provider layer" above.

## Deployment (Vercel)

The app is deployed to Vercel with **`POST_JOB_METHOD=extension`**: the Playwright method needs a browser and a screen on the server and waits for the user to close its window, which a serverless host can't do, so posting goes through the browser extension instead (see "Posting: browser extension").

- **`POST_JOB_METHOD`** (`extension` | `browser` | `off`) is read in `next.config.ts` at build time and inlined into server and browser code (`lib/features.ts`). Unset, it's `extension` when Vercel's `VERCEL` system env var is present and `browser` everywhere else, so local `npm run dev` keeps the Playwright flow; set `POST_JOB_METHOD=extension` locally to work on the extension. Changing it needs a rebuild/redeploy. `/api/post-job` `import()`s `automation/postJob` and `automation/errors` only for the browser method: both import `playwright`, which can't even be loaded on Vercel (its file tracing misses `playwright-core/browsers.json`), so a static import crashed the route with a bare 500.
- **Vercel env vars:** `AI_PROVIDER` + that provider's key (`GEMINI_API_KEY`), optionally `AI_MODEL` and `API_GATEWAY_URL`. The `JOB_SITE_*` and `PLAYWRIGHT_*` vars are only for the Playwright method and aren't needed there. `.env.local` is git-ignored and never uploaded.
- **Limits that matter on Vercel:** request bodies are capped at 4.5 MB, hence `MAX_UPLOAD_BYTES` = 4 MB. `/api/extract` sets `maxDuration = 180` (Gemini's 3 × 60 s attempts, matching the upload page's 180 s timeout), which needs Fluid compute (the default for new projects); without it, Hobby caps functions at 60 s and the deploy is rejected.
- `lib/locations/server.ts`'s 24 h cache is per function instance on Vercel, so a cold start refetches the location tree. That's harmless.
- `vercel.json` sets the functions region to `sin1` (Singapore, near Sri Lanka) and turns on Fluid compute. The first deploy asked for `bom1` but ran in `sin1` regardless. The gateway (`api.ikman.lk`) and Gemini are both reachable from there. `.vercelignore` keeps `.env*`, `.next`, `node_modules` and `.git` out of CLI uploads.
- Deployed with the Vercel CLI from the working tree (`npx vercel deploy --prod`), not from GitHub, to the personal Hobby scope of the developer's account. Hobby is for non-commercial use, so a company tool should move to a team on a paid plan.
